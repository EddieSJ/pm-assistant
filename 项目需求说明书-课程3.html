1引言

1.1 编写目的

本文档定义「项目管理智能助手」平台在课程3「计划与资源智能调度」阶段的功能需求、业务规则与约束，作为开发、验收与后续迭代的基准。课程3 的核心目标：延续同一个项目（CY-DCM-2026-01）与同一个私人 Agent 的能力生长路径，在课程1「文档事实」与课程2「状态判断」之上补齐最后一环——把偏差与风险转成未来行动，构建一条可检查、可调整、可追溯的计划闭环：判断文件效力 → 建立统一 WBS 与稳定 ID → 归集五类约束 → 确定性排程形成计划 V1 → 多视图联动呈现 → 资源负荷与冲突处理 → 关键路径与冲突预警 → 追加事件派生 V2 与备选方案 → 人工确认责任动作并保存证据。

一句话概括三代能力的分工：事实是底座，状态形成判断，计划才把判断转成未来行动。

1.2 项目范围

  • 在范围（课程3 规划，全部待实现）：计划输入与文件效力识别、WBS 映射与稳定 ID、依赖与约束确认状态、工作日历与确定性排程、交互式计划界面、资源负荷与分配、关键路径与冲突预警、计划版本与动态调整、方案比较、建议六要素与人工确认关卡、证据与审计轨迹（见第 3 节 F-63~F-90）。
  • 复用（课程1 / 课程2 已实现）：课程1 的文档事实底座（合同、计划责任、会议事实、来源与记忆）、项目看板与智能聊天、三层记忆与记忆治理；课程2 的截至 2027-03-31 的状态结论（指标、趋势、预警与决策依据）。以上既有事实底座直接复用，课程3 不重复做文档整理与数据接入。
  • 不在范围：D01—D04 动态事件文件本期不授权（由教师在 V1 冻结后发放，见 6.1）；多用户权限体系、移动端、向量数据库检索（当前版本不引入）。

1.3 目标用户

项目经理（个人使用），服务于虚构企业「上海澄岳智能装备有限公司」的教学场景。课程3 阶段项目经理需要回答的不再是「项目现在怎样」，而是每天必须面对的执行三问：4 月 1 日先做什么？谁来做？哪些任务不能同时开始？什么时候能够上线和验收？

1.4 术语定义

术语定义
计划因果链文件效力 → WBS → 约束 → 排程 → 呈现 → 资源 → 关键路径 → 版本与调整 的单一管理链路，八项能力必须沿此链条工作
文件效力一份材料对「未来执行」的约束强度；效力强（历史/已批准）→ 效力弱（预测/待批准）八类分级（见 6.3）
效力四问判定一个日期能否进入排程的四个问题：谁发布？何时生效？是否已批准？能否追溯？
稳定 ID不被重命名、重排或换表破坏的对象标识；活动 activity_id、父任务 task_id、资源 resource_id、里程碑 milestone_id、来源 source_record_id、版本 plan_version、事件 event_id
WBSWork Breakdown Structure，工作分解结构；父任务 → 活动 → 交付物的层级组织
五类约束依赖关系、工作日历、资源容量、外部窗口、质量门——共同决定项目活动的最早、最晚与基准日期
确定性排程由可复核的规则引擎计算日期，不含主观判断；输入为计划起点、工作日历、确认后工期、依赖类型、资源日期区间容量、质量门
关键路径控制交付日期的活动链，可计算、可复核；判据包括前置关系连续、总时差接近 0、质量门不可压缩、受窗口与签署限制
总时差（Float）活动在不影响总工期的前提下可延迟的时间；关键路径活动总时差接近 0
资源可用性日期区间容量 − 其他已承诺工作；「资源表里有这个人」不等于「这一天可被项目使用」
计划版本V1（冻结基准）/ V2（追加事件后派生）；每个版本保留输入快照、计算参数、日期结果、资源分配与恢复点
备选方案（情景）S1 / S2 / S3 等并列情景，各自记录条件、结果与代价；情景不等于已批准计划
事件效力判定对新增事件判定为立即生效 / 条件生效 / 仅情景模拟 / 仅形成比对任务，再决定重算、模拟、记录或等待确认
责任动作资源批准、正式变更、生产切换、UAT 签署、最终验收五类必须由人确认的动作
质量门不可作为进度优化代价的质量与批准边界（P1/P2 缺陷 = 0、总体通过率 ≥ 95%、数据准确率 ≥ 99.5%、Go/No-Go 与 UAT 签署由责任人人工完成）

2项目概述

2.1 背景

课程2 已解决「项目现在怎样」，但监控能证明问题存在，却不能自动给出可执行安排。课程2 状态卡片显示：状态日 2027-03-31、计划进度 93.8%、实际进度 82.5%、SPI 0.880、CPI 0.934，关键剩余任务 T10 集成测试 62%、T11 用户验收测试 38%、T13 上线准备 12%。这些结论回答了「发生了什么」，却没有回答「4 月 1 日先做什么、谁来做、哪些任务不能同时开始、什么时候能上线和验收」。

更深层的问题在于：未来计划藏在多份效力不同的文件里。项目总控进度计划（控制基线、当前预测）、各专业剩余工作反馈（本地工作项、工期估算、依赖与候选资源）、资源池及可用日历（人员能力、日期区间、每日容量与既有承诺）、关键测试资源借调申请（待批准情景）、供应商进场计划（外部承诺与前置条件）、生产环境与变更窗口通知（材料截止、可用窗口、运维限制）、协调会纪要（已决定事项、行动项、讨论项与待决事项）——这些材料发布主体不同、批准状态不同、可追溯程度不同。若不加区分地排进甘特图，只会得到精确的假计划。

课程3 的输入不是再做一次七类数据分析，而是判断哪些企业文件能够约束未来执行。

2.2 建设目标

延续同一个 Agent，把课程2 发现的偏差与风险变成未来执行方案：

  1. 可执行：明确剩余工作、顺序、责任与期限——六个问题落到同一 activity_id 与同一计划版本。
  2. 可调整：新事件进入后快速形成版本与备选方案，派生而非覆盖。
  3. 可追溯：日期、资源和建议能够回到来源与规则。
  4. 可负责：责任动作停在人工确认前，Agent 不执行责任动作。
  5. 不越界：任何进度优化都不得偷换质量门与批准边界。

2.3 技术栈（概要）

沿用课程1 / 课程2 技术栈（React 18 + Vite 5 ｜ FastAPI ｜ SQLite ｜ 千问 qwen-plus），新增「计划与资源智能调度」板块：确定性排程引擎（依赖 + 日历 + 工期 + 资源容量 + 关键路径计算）、计划版本与情景管理、资源负荷计算、冲突预警、证据索引与恢复点。数据层需新增计划材料、活动与 WBS、依赖、资源与日历、计划版本、事件、冲突预警、证据等实体（详见第 6 节与第 9 节）。详见《技术架构.md》。

7业务规则与约束

7.1 三代能力链的衔接

同一个项目（CY-DCM-2026-01）、同一个私人 Agent，能力持续生长：

阶段回答的问题核心输出

事实是底座，状态形成判断，计划才把判断转成未来行动。课程3 不是重复监控，而是把偏差转成未来执行方案。

7.2 文件效力分级与效力四问

先判定文件效力，再决定它如何进入计划。效力强（历史 / 已批准）到效力弱（预测 / 待批准）共八类（见 6.3）；任何日期进入排程前必须通过效力四问（谁发布、何时生效、是否批准、能否追溯）。把无效日期排进甘特图，只会得到精确的假计划。

7.3 五类管理性错误（防错清单）

看起来完整的甘特图，可能同时包含五类隐藏但致命的管理性错误：

#错误后果表现
1用预测日期覆盖批准基线开始日期很精确，资源却无法到位
2把资源申请当作已获批容量里程碑看似可达，责任人却没有承诺
3把会议讨论当作正式决定决定缺乏批准依据，执行时被推翻
4忽略人员每日容量和既有承诺同一资源被重复占用，形成真实冲突
5为追赶日期压缩测试、验收或签署门关键路径被标红，计算依据却无法复核

图画得越精确，错误约束造成的误导越大。

7.4 依赖遗漏的放大链条

漏掉一条依赖，延期与成本会沿链条放大：依赖节点被忽略 → 并行变为串行 → 资源冲突与排队等待 → 关键路径被迫绕行 → 生产窗口或验收节点错失无法补救 → 加班、外援、等待与变更成本增加 → 最终交付继续后移。

计划错误的危害不在一张图，而在它会错误地组织真实资源与责任。影响逐级放大，越往后越难追回。

7.5 五类约束共同作用

依赖关系、工作日历、资源容量、外部窗口、质量门五类约束共同作用，才能计算出活动的最早、最晚与基准日期（见 6.4）。任何一个约束缺失，得到的日期都只是「看起来合理」，而不是真正可执行的计划。

7.6 质量门与批准边界不可作为「优化」手段

本项目不可放松的质量门：P1/P2 缺陷 = 0、总体通过率 ≥ 95%、数据准确率 ≥ 99.5%、Go/No-Go 必须由责任人决定、UAT 签署与最终验收必须人工完成。

禁止作为「优化」的五项动作：取消全量回归、把申请改写成批准、强行进入生产窗口、用无限加班替代资源决策、自动签署 / 验收 / 正式变更。

日期目标不能凌驾于质量与责任之上；计划优化只能调整可调整项，不能偷偷放松质量门和批准边界。

7.7 六个问题与同一计划版本

一个可执行的计划必须答清六个问题，且六个问题的答案必须落到同一 activity_id 和同一计划版本：

问题检查内容
做什么？剩余工作与交付物是否完整
谁来做？责任资源与候选资源是否可用
哪里冲突？容量、依赖、窗口和里程碑如何影响
先后如何？前置关系和质量门是否成立
何时做？工作日历、窗口和工期如何计算
谁来确认？哪些事项需要资源、变更、运维或验收责任人批准

缺少任何一个问题，计划都可能只是一张不能执行的时间图。

7.8 规则算数字、Agent 做解释、人承担责任

三层分工不可混淆：

层职责边界
确定性排程引擎依赖、日历、工期、资源容量、关键路径计算可复核规则，确定性计算，不含主观判断
交互式计划界面看板、待办、WBS、甘特、资源负荷、预警、版本比较多视图共享同一计划与同一版本
人工决策与责任确认资源批准、正式变更、生产切换、UAT 签署、最终验收责任动作必须由人完成
千问（Agent）解释原因、归纳影响、比较方案、生成建议草案不得编造日期、不得放松规则、不得替人批准

数字由规则计算，建议由 Agent 解释，责任由人承担。

7.9 变更同步所有管理视图

一次活动日期或资源变化，必须同步七项视图：WBS 结构保持一致、甘特日期重新计算、资源负荷同步变化、关键路径重新识别、看板与待办更新、冲突预警重新评估、计划版本留下差异。所有视图共享同一 activity_id、同一规则和同一版本，来源与确认状态仍可追溯。

Agent 的价值不是多画几张图，而是让计划对象、证据和变化保持一致。

7.10 调整派生新版本，不抹掉旧计划

动态调整是追加事件与派生版本，不是把昨天的计划改到看不见：V1 冻结后追加 D01—D04 事件，先判断事件效力（立即生效 / 条件生效 / 仅情景模拟 / 仅形成比对任务），再派生 V2 与 S1 / S2 / S3 备选方案；每个变化保留 event_id、来源、时间、影响对象与确认状态。历史版本始终保留。

7.11 建议六要素与人工确认关卡

一条合格的决策支持建议必须包含六个要素：具体对象、证据、责任人、期限、替代方案、待确认事项。人工确认关卡覆盖五类责任动作：资源批准、正式变更、生产切换、UAT 签署、最终验收。Agent 只生成建议草案，不执行责任动作。

建议只有能够被确认、分配、跟踪和复核，才真正支持项目决策。
