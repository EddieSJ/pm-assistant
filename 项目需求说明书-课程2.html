1引言

1.1 编写目的

本文档定义「项目管理智能助手」平台在课程2「数据智能与决策支持」阶段的功能需求、业务规则与约束。课程2 的核心目标：在课程1 已建成的「智能文档与知识工作流」基础上，让项目数据从「被记录」走向「能判断」，构建一条可验证的数据决策链。

1.2 项目范围

  • 在范围（课程2 待实现）：数据接入（七类数据源）、数据清洗、EVM 指标分析、可视化看板、趋势预测、风险预警、决策建议。
  • 复用（课程1 已实现）：项目全局管理、文件自动识别、项目看板、智能聊天、Word 文档生成、三层记忆（作为工程基础，直接复用与迭代）。
  • 不在范围：多用户权限体系、云端部署、移动端、向量数据库检索（当前版本不引入）。

1.3 目标用户

项目经理（个人使用），服务于虚构企业「上海澄岳智能装备有限公司」的教学场景。

1.4 术语定义

术语定义
EVM（挣值管理）Earned Value Management，用挣值度量项目进度与成本绩效的量化方法
PV（计划价值）Planned Value，计划到某时间点应完成工作的预算价值
EV（挣值）Earned Value，实际完成工作的预算价值
AC（实际成本）Actual Cost，实际完成工作所发生的成本
SPI（进度绩效指数）Schedule Performance Index，EV / PV，衡量进度效率
CPI（成本绩效指数）Cost Performance Index，EV / AC，衡量成本效率
EAC（完工估算）Estimate At Completion，BAC / CPI，预计完工总成本
数据治理四原则可控、可追溯、可复核、可比较
七类数据源计划 / 成本 / 人工与质量 / 风险 / 质量 / 采购 / 合同 七类结构化数据文件夹

2项目概述

2.1 背景

课程1 已让项目文档「被理解、被沉淀」，但项目经理面对的核心痛点仍在——数据分散（进度、人员、成本、质量、风险各自独立）、口径不一（日期、金额、比例、状态难以直接比较）、更新滞后（看到的多是历史结果）、缺少关联（单张表无法解释问题如何相互影响）。项目管理缺的不是表格数量，而是统一、及时、可关联的判断依据。

2.2 建设目标

在课程1 工程基础上持续迭代，让同一个 Agent 从「知识工作」延伸到「数据决策」：

  1. 连接：七类数据源进入同一视图，项目状态才可能完整。
  2. 治理：数据先治理，才能成为可引用的项目事实。
  3. 判断：指标分析 + 趋势预测 + 风险预警，让「异常」可被及时发现。
  4. 行动：决策建议可分配、可跟踪、可复核，最终由人确认。

2.3 技术栈（概要）

沿用课程1 技术栈（React 18 + Vite 5 ｜ FastAPI ｜ SQLite ｜ 千问 qwen-plus），新增 CSV/XLSX 结构化解析、EVM 指标引擎、时间快照与预警能力。详见《技术架构.md》。

6数据需求

6.1 数据来源（课程2：七类数据源）

课程2 新增七类结构化数据源文件夹，用户授权后选择多个连接，仅只读读取：

  1. 01_计划数据：计划进度、里程碑、任务计划工时等。
  2. 02_成本数据：预算、实际成本、费用明细等。
  3. 03_人工与质量：人员主数据、工时、加班、缺陷记录等。
  4. 04_风险数据：风险登记册、风险等级、开放风险等。
  5. 05_质量数据：缺陷、验收、测试结果等。
  6. 06_采购数据：采购订单、交付、验收状态等。
  7. 07_合同数据：合同金额、里程碑、交付节点等。

课程2 数据源格式以 .csv / .xlsx 为主，需升级 parsers.py 支持 .csv 并做列级结构化解析（见 F-40）。

6.2 指标公式（EVM 挣值管理）

  • 进度指标：计划进度（PV）、实际进度（EV）、偏差（EV − PV）、SPI = EV / PV。
  • 成本指标：预算（BAC）、实际成本（AC）、CPI = EV / AC、EAC = BAC / CPI、完工偏差 = BAC − EAC。
  • 人员指标：计划工时、实际工时、加班工时、利用率 = 实际工时 / 计划工时。
  • 质量与风险指标：高级缺陷数、开放风险数、风险分（按风险等级加权）。
  • 工程与采购指标：延期里程碑数、延期交付数、验收状态（通过 / 待验收 / 延期）。

每个指标均可溯源到公式、数据范围与原始记录（见 F-50），不凭空造数、不自动证明因果。

7业务规则与约束

7.1 数据治理四原则

  1. 可控：原始文件只读，清洗与标准化全程留痕，不悄悄改值；模糊问题标「待确认」由人工确认。
  2. 可追溯：来源标签 + 时间戳审计层，指标 / 预测 / 建议可回到公式、数据范围与原始记录。
  3. 可复核：预测与建议说明方法、基线、限制，输出可复核的行动草案，关键节点待人工确认。
  4. 可比较：多时间节点快照（T1/T2/T3 + 修订号）历史不覆盖，变化趋势可对比。

7.2 决策支持必须回答「发生什么、为什么、怎么办」

  1. 发生了什么：指标、差距与异常（事实）。
  2. 为什么发生：跨表证据与影响路径（解释）。
  3. 现在怎么办：行动、责任、期限与确认（行动）。

只给结论不是决策支持，能解释并能行动才是。

7.3 预警落到「对象、原因、责任人、期限」

每条预警包含对象 ID、证据、责任人、期限与来源。好的预警必须让管理者知道风险在哪里、为什么、由谁处理。

7.4 数据不替代判断

数据与指标仅提供决策支持，最终决策由人负责并人工确认；预测不把不确定写成确定事实；跨表证据不自动宣称因果。

8后续迭代约定

以下为项目维护的固定工作流，团队成员（含 Agent 角色）须遵守。

  1. 先文档后代码：任何功能变更，先更新本《项目需求说明书》，再更新代码。
  2. 代码交给 coder：代码层面的改动由 coder 角色负责实现，不越过该角色直接改代码。
  3. 资产同仓：技术架构、需求说明书与代码同仓维护，保持同步。
  4. 双轨同步：本 .md 是唯一编辑入口，修改后须重新生成对应 .html 交付物，保证「源稿」与「交付物」一致。
