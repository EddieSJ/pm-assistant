1引言

1.1 编写目的

本文档定义「项目管理智能助手」平台在课程1「智能文档与知识工作流」阶段的功能需求、业务规则与约束，作为开发、验收与后续迭代的基准。平台是一个私人本地部署的项目管理智能体 Web 应用：通过外部 env 接入大模型 API，自动识别项目文件夹中的各类文档，提取关键信息并沉淀到本地记忆体，实现「有据可依、有理有据、有记忆、有标准」的项目管理中枢。

1.2 项目范围

  • 在范围（课程1 已实现）：项目全局管理、文件自动识别、项目看板可视化、智能聊天问答、Word 文档生成、三层记忆沉淀。
  • 不在范围：多用户权限体系、云端部署、移动端、向量数据库检索（当前版本不引入）；课程2「数据智能与决策支持」规划功能（见《项目需求说明书-课程2》）。

1.3 目标用户

项目经理（个人使用），服务于虚构企业「上海澄岳智能装备有限公司」的教学场景。

1.4 术语定义

证据链文件 → 证据 → 事实 → 判断 → 行动 → 记忆沉淀 的追溯链路
四道门事实门 → 结构门 → 可用性门 → 风险门 的输出纪律
授权-停下缺料 / 不可验证 / 权限不足 / 未确认时主动停下，不编造

2项目概述

2.1 背景

项目经理面对大量项目文档（标书、合同、计划、团队清单、干系人清单、会议记录、财务资料、问题风险记录），需要快速、准确地掌握项目全貌并支持决策。传统人工整理耗时且易遗漏。项目时间真正耗在「找、核、写、追」四件事上——信息分散定位难、口径核对难、反复改写低效、责任闭环易缺失。

2.2 建设目标

构建一个「有据可依、有理有据、有记忆、有标准」的本地项目管理中枢：

  1. 有据可依：所有结论可追溯到具体来源文件与原文。
  2. 有理有据：回答基于已确认事实，不编造。
  3. 有记忆：三层记忆沉淀，杜绝幻觉与重复劳动。
  4. 有标准：遵循企业知识库与文件处理约束库的规范。

2.3 技术栈（概要）

React 18 + Vite 5（前端）｜ FastAPI（后端）｜ SQLite（数据库）｜ 阿里云百炼 DashScope 千问 qwen-plus（大模型）。详见《技术架构.md》。

7业务规则与约束

7.1 输出纪律（四道门）

  1. 事实门：结论基于已确认事实 / 证据，标注来源，区分「事实 / 推断 / 待确认」。
  2. 结构门：结构完整、条理清晰，遵循约束库格式要求。
  3. 可用性门：输出可直接用于决策与执行。
  4. 风险门：不越权、不替授权审批，财务 / 合同 / 人事结论标记「需人工复核」。

7.2 授权-停下

遇到以下任一情况必须主动停下并说明，绝不编造：缺关键材料；结论不可验证；权限不足；事项未确认。

7.3 输出要求

  • 每个关键结论标注来源，格式 [来源: 文件名/章节]。
  • 财务金额保留原始口径（含税 / 不含税、当期 / 累计）。
  • 人名保留原文，疑似错字不得擅自合并。
  • 不得生成不存在的人员、联系方式、金额、日期、审批或签章。

7.4 事实状态判定

  • 文件明确写明的 → confirmed（已确认）。
  • 合理推测 → provisional（待核实）。
  • 无法确定 → needs_confirmation（待确认）。

7.5 指令三层分层治理

  1. L1 系统指令（build_system_instruction()）：身份、原则、权限/风险边界、四道门、授权-停下、输出要求、企业知识库、约束库。长期不变，进入 system role。
  2. L2 工作流指令（build_workflow_instruction(task_type)）：task_type ∈ {analyze, answer, docgen}，各含步骤、校验点、输出模板。
  3. L3 任务指令：本次任务目标、材料、对象、时间要求，动态拼入 user message 头部。

7.6 检索与上下文边界

检索召回策略（零新增依赖，关键词打分召回）：

  • 提取问题关键词：正则提取长度 ≥2 的汉字片段 + 英文单词，去重。
  • 对每条候选按字段拼接做关键词重叠打分（fact=field+value+category；action=action+owner；finance=item+category；stakeholder=name+organization+role；conflict=description）。
  • score>0 按分数降序取 Top-K：facts≤20、actions≤10、finance≤10、stakeholders≤8、conflicts≤12。
  • 召回为空则不注入项目事实，并说明「未检索到与问题直接相关的事实」。

上下文边界三分：

  1. 通用规则上下文：企业知识库 + 约束库 → system role（L1 承载）。
  2. 项目事实上下文：召回条目 → user message（L3 承载）。
  3. 当前任务上下文：本次问题 + 工作记忆历史 → user message（L3 承载）。

8后续迭代约定

以下为项目维护的固定工作流，团队成员（含 Agent 角色）须遵守。

  1. 先文档后代码：任何功能变更，先更新本《项目需求说明书》，再更新代码。
  2. 代码交给 coder：代码层面的改动由 coder 角色负责实现，不越过该角色直接改代码。
  3. 资产同仓：技术架构、需求说明书与代码同仓维护，保持同步。
  4. 双轨同步：本 .md 是唯一编辑入口，修改后须重新生成对应 .html 交付物，保证「源稿」与「交付物」一致。
